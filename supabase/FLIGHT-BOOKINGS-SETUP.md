# Flight booking requests — Supabase setup

The customer dashboard reads from `public.flight_bookings`. Before enabling this feature on a deployed site:

1. Open the Supabase project connected in `js/auth-config.js`.
2. Open **SQL Editor**.
3. Run the complete contents of `supabase/flight-bookings.sql`.
4. Confirm the table exists and Row Level Security is enabled.
5. Sign in with two separate disposable test accounts.
6. From Account A, search a demo flight and click **Confirm booking request**.
7. Confirm the new request appears in Account A's dashboard.
8. Sign out and sign in as Account B. Confirm Account A's booking is not visible.
9. Attempt to select Account A's booking while authenticated as Account B; the RLS policy must return no rows.

## What the current action means

The flight page is using mock inventory. Clicking **Confirm booking request** inserts a record with status `pending_confirmation`. It saves the selected demo itinerary and passenger counts against the authenticated user's Supabase Auth UUID.

It does **not**:
- reserve an airline seat;
- validate the sample flight number, time, baggage or fare;
- charge a customer;
- issue a PNR or e-ticket;
- mark a booking as confirmed.

The displayed demo fare is stored only as a reference to the selected mock option. It is not a quote or payment amount.

## Security model

- Customers can SELECT only rows where `user_id = auth.uid()`.
- Customers can INSERT only rows where `user_id = auth.uid()`.
- Customers have no UPDATE or DELETE permission through the browser client.
- The booking reference and initial status are generated by database defaults.
- Actual confirmation/cancellation should be performed by a trusted server-side workflow after live inventory and payment integrations exist.

Do not put Supabase service-role keys or Travelpayouts secrets in browser code.
